# SudokuV2 — согласованные требования и проектные решения

Дата: 2026-10-11. Статус: одобрена пользователем, реализация начата.

Основание: ответы пользователя в этом чате и текущий функциональный анализ
`docs/sudoku-v2-functional-analysis.md`. План: `../plans/2026-10-11-sudoku-v2.md`.

## Подтверждённые требования

- Полностью перейти на название SudokuV2: исходники, интерфейс, документацию,
  URL, идентификаторы, ключи хранения, конфигурацию тестов и текущую Git-ветку.
- Три независимые панели: своя доска, управление, соперники. На компьютере GridStack
  позволяет перемещать панели и менять их размеры. Раскладка живёт только в памяти
  страницы, после reload сбрасывается. На телефоне функция перемещения не нужна.
- Поддержать 9×9 и 16×16 сейчас, включая `game/management/commands/fillSudoku.py`.
  Геометрические алгоритмы используют N и B = isqrt(N), где B² = N.
- Бонус определяется бэком при первом правильном заполнении бонусной клетки.
  После стирания, повторного ввода и reconnect он повторно не выдаётся.
- Клеточные бонусы действуют на текущих оппонентов; при отсутствии целей пропускаются
  и считаются использованными. Параметры одного события едины для всех целей.
- SWAP меняет две строки или два столбца исключительно внутри одной группы B.
  Канонические индексы, значения и решение не перемещаются в хранилище; сохраняется
  перестановка отображения до следующей генерации доски.
- Временные эффекты: SHADOW_BOX (размытие), ROLL (вращение целого блока), DANCE
  (покачивание), GRAYSCALE (обесцвечивание), PULSE (пульсация прозрачности).
  Длительность устанавливает сервер, по умолчанию 30 секунд.
- Каждый эффект имеет независимый экземпляр: одинаковые эффекты на одном блоке
  накладываются, каждый снимается собственным setTimeout. Ни замены, ни продления
  уже существующего экземпляра. Бонусы и эффекты видны на досках оппонентов;
  вкладки оппонентов показывают индикаторы действующих эффектов.
- Один существующий Twitch-бот обслуживает несколько лобби. Один канал связан
  с одним лобби и подключившим его игроком; в лобби возможно несколько каналов.
- Команды: `!<command> <name> <args>`. Имя по умолчанию `*` (все цели).
  Недопустимый параметр заменяется своим значением по умолчанию.
- КД по умолчанию 0. Он задаётся на сайте при подключении Twitch. Повторная
  регистрация того же канала в том же лобби обновляет только КД, без второго бота
  или новой подписки. В интерфейсе нужна кнопка отключения.
- Сейчас нужны команды чата; будущие награды за баллы должны подключаться через
  тот же серверный интерфейс эффектов, без переписывания игрового слоя.
- Каждый этап реализации тестирует и проверяет свежий субагент Astra 6
  (`gpt-6-astra`) по навыку `find-bugs`. Исправления проверяются до следующего этапа.

## Решения, конкретизирующие ответы

Это рабочие значения для реализации и просмотра плана; они не выдаются за отдельные
пожелания пользователя.

### Имена и границы

Название `SudokuV2`, Python-пакет/namespace/static `sudoku_v2`, классы
`SudokuV2Consumer`, `SudokuV2Service`, `SudokuV2Storage`, `SudokuV2Error`,
`SudokuV2Config`; HTTP `/sudoku-v2/`, WS `/ws/sudoku-v2/`, Redis `sudoku-v2:`,
ветка `codex/sudoku-v2`, тестовая переменная `SUDOKU_V2_TEST_REDIS_URL`.
Переименовывается эта версия приложения; старые `game`, `voice`, `bunker` не
становятся SudokuV2. История Git не переписывается, удалённые ветки не удаляются.
Все отслеживаемые упоминания старого бренда и имена его файлов обновляются.
Сторонние незавершённые документы не менять. План и спецификацию также обновить
после rename, убрав переходные старые пути.

Новый namespace не читает старые сессии/Redis/localStorage/IndexedDB этого приложения.
Переход требует повторного входа и генерации; не удалять старые данные wildcard-
командами. Сохраняется существующее правило очистки комнаты после последнего игрока.

### Размеры, хранение задач и генератор

В этой поставке каталог размеров `[9, 16]`. Другие N отклоняются, но геометрия
параметризована. Использовать существующие SudokuBoard/SudokuCell, без изменения
SQL-схемы: размер определяется количеством клеток (81/256), затем проверяются
точные индексы и значения. QuerySet.annotate(Count('sudokucell')) фильтруется до
случайного выбора. Старый `game` по умолчанию выбирает только 81-клеточные задачи,
чтобы добавление 16×16 не сломало его доску. Сейчас миграции исключены из Git;
для этой функции не заводить независимую историю миграций.

Генерация полного решения: базовый латинский шаблон
`(B * (r % B) + r // B + c) % N`, перемешивание символов, групп и строк/столбцов
внутри групп, случайная транспозиция. После удаления каждой подсказки проверять
единственность решения solver-ом MRV с битовыми масками и остановкой на втором
решении. Недоказанная за бюджет единственность означает возврат подсказки.

Сложность остаётся категорией количества пустых клеток, а не оценкой человеческих
техник. Границы масштабируются из Difficulty.top_limit: floor(top_limit*N²/81).
Для 9: 30/55/81; для 16: 94/173/256. Нижняя граница следующей категории — предыдущая
верхняя + 1; для easy минимум одна пустая клетка. Не маркировать более лёгкую
задачу как hard при исчерпании попыток.

CLI: `fillSudoku --sizes 9 16 --minimum 10 --seed <int> --max-seconds 30`.
Без флагов создаются недостающие задачи обоих размеров до 10 на сложность/размер.
30 секунд — общий бюджет поиска одной следующей задачи (до 10 попыток), а не
гарантированная скорость. При исчерпании — CommandError с размером/сложностью;
уже полностью сохранённые задачи остаются. Каждая доска с клетками записывается
в transaction.atomic. Повторный запуск учитывает только корректные полные задачи.
Проверка уникальности ограничена также 100000 узлами на одну попытку удаления.

На 16×16 отображать десятичные 1…16; клавиши 1…9 и A…G вводят 1…9 и 10…16,
0/Delete/Backspace стирают. Кнопки всегда показывают 1…N. Встроенные SVG-наборы
дополнить до 16 символов; поведение неполного пользовательского файла сохранить.
Размер в селекторе — размер следующей генерации: текущая доска и её ввод используют
board.size. При успешной генерации сервер возвращает автору обновлённый config с
allowedValues=['', 1…N]; другим участникам config не рассылается.
Запрос set_context включает generationId действующей на клиенте доски (null до
первой генерации). Устаревший запрос получает stale_context; клиент обновляет
снимок и повторяет несохранённые предпочтения, не подтверждая этим ожидающие ходы.

### Эффекты и общий протокол

Публичная доска дополнительно содержит `rowOrder`, `columnOrder` (перестановки
0…N−1), `consumedBonusCells` (канонические индексы), `activeEffects`.
Эффект: `{id, kind, params, startsAt, expiresAt}`; timestamps — серверные ms.
Для SWAP expiresAt=null; его результат хранится в rowOrder/columnOrder, не в
растущем списке завершённых эффектов. Вкладка показывает SWAP, если перестановка
не тождественная. Для остальных params содержит box (0-based), expiresAt=startsAt
+ настроенная длительность. Каждый отдельный запуск получает новый id.

Конверт `{kind,data}` сохраняется. Рассылка бонуса:
`bonus_applied: {eventId, source, kind, params, targets, serverNow}`,
где source=`{type:'cell'|'twitch_chat'|'twitch_reward', name}`, а targets — полные
публичные доски затронутых игроков с generationId/revision. Для cell в targets
также входит доска источника с подтверждённым ходом/потреблением бонуса. Это дельта,
не полный список участников; она не должна удалить остальных игроков из state.
Эффект может восстановиться из обычного полного снимка после пропуска события.
Повторная доставка eventId/эффекта не запускает его заново. Не путать уведомление
о бонусе с подтверждением ожидающего собственного set_value.

Запись хода, потребление бонуса и изменения всех целей — одна Redis-транзакция
с проверкой ревизий, поколений и действующих presence. Случайные параметры выбираются
бэком один раз для успешного события. Рассылка выполняется после commit. При разрыве
между commit и рассылкой снимок остаётся источником истины; не вводить обещание
exactly-once доставки WebSocket. completed/requiresGeneration/отсутствующие доски
не являются целями. Новые игроки после фиксации события эффект не получают.

Для смешанного лобби 9×9/16×16 один номер блока допустим у всех: 0…min(N)−1.
Для SWAP выбирать пару из пересечения допустимых пар всех целей:
`a != b`, `0 <= a,b < min(N)`, `a//isqrt(N) == b//isqrt(N)` для каждого N.
Так параметры действительно одинаковы и перестановка корректна для всех досок.

Клиент применяет перестановки к отображению и вычисляет обратное отображение для
стрелок/подсветки; data-cell-index остаётся каноническим. Временные эффекты относятся
к визуальному блоку; swap внутри группы не переносит клетки в чужие блоки.
Рендер сохраняет DOM клеток. Отдельные вложенные visual wrappers по id дают
независимость blur/transform/opacity; таймер удаляет только свой wrapper. Истечение
определяется expiresAt с поправкой serverNow: reload не выдаёт ещё 30 секунд.
На visibilitychange повторно сверить время; dispose/перегенерация очищают таймеры.

### Панели

GridStack 14.0.0, локальные vendor JS/CSS и лицензия; версия фиксируется. Включать
только при `(min-width: 900px) and (pointer: fine)`. Ни storage, ни config, ни WS
не содержат раскладку. Drag доступен только через заголовок/ручку, чтобы не забирать
клики у клеток. Панель управления включает значения, режимы и генерацию.
При переходе на узкий экран фиксированный порядок: своя доска, управление, соперники.
При возврате на широкий экран допустимо восстановить раскладку из памяти этой же
страницы. Появление/уход соперников не пересоздаёт собственную доску. Доски квадратные;
resize панели не обрезает кнопки/цифры. На 16×16 узкий экран сохраняет доступные
кнопки ввода и читаемые двухзначные символы без горизонтальной прокрутки страницы.

### Twitch: транспорт, маршрутизация и команды

Изучен `C:/Users/jollyray/Desktop/importantThings/python/sudoku-desktop/bot.py`:
TwitchIO старого API, один bot.websocket, команды swap/shadow, локальный WS 3782.
Реализацию перенести в этот репозиторий отдельной Django management command
`run_twitch_bot`; внешний desktop-файл оставить источником для сравнения.
Сохранить аккаунт бота и OAuth из окружения, не копировать встроенный fallback-токен.
Перед реальным запуском заменить найденный встроенный токен, если он ещё действующий.

Для текущей задачи выбран адаптер Twitch IRC по TLS на asyncio из стандартной
библиотеки: он соответствует существующей интеграции и не требует нового согласия
стримеров. Twitch рекомендует EventSub для новых полнофункциональных ботов; будущий
EventSub-адаптер подключается к ExternalBonusCommand, как и награды. Сейчас не
реализуются ни webhook, ни награды. У нового процесса нет входящего публичного
порта или игрового WS: он получает команды из Twitch и вызывает общий игровой
сервис, затем channel_layer.group_send по общему helper-у имени группы лобби.

Registry Redis хранит `{channel, lobby, ownerName, cooldownSeconds, bindingId,
registeredAt, lastAppliedAt}`. КД общий для всех бонус-команд этого канала,
отсчитывается от последнего успешно применённого события. Значение сайта — целое
0…86400, default 0. Повтор регистрации сохраняет bindingId/owner/lastAppliedAt,
меняет только cooldownSeconds. Чужое лобби не перехватывает действующую связь.
Изменение/отключение доступны подключившему игроку по текущей session/presence;
второй игрок получает понятный отказ. Одновременно активные регистрации одного
канала атомарно разрешаются в одну связь. Без присутствующего owner команды
пропускаются; связь сохраняется, пока комната существует, или до кнопки disconnect.
Последняя очистка комнаты удаляет её связи; worker при сверке также убирает
осиротевшие связи. Старая связь не переезжает в новое поколение комнаты с тем же
именем (roomEpoch и bindingId проверяются при обработке).

Worker один на bot user id: lease 30 s, renew 10 s, при утрате lease прекращает
приём/применение. Сверка реестра каждые 2 s; JOIN/PART только по изменившимся связям,
повтор регистрации не делает JOIN. Начальные консервативные лимиты: 100 каналов,
20 JOIN за 10 секунд и 20 авторизаций за 10 секунд на аккаунт. Не полагаться на
исключения для moderator/verified. Превышение отражается статусом pending/error
в UI, не бесконечным спамом.
На перезапуске восстанавливать каналы из действующего реестра. PING/PONG, RECONNECT,
повтор авторизации и отключения обязательны. OAuth валидируется при запуске и
каждый час. При invalid token остановить с auth_error; новый токен задаёт оператор
(автоматический OAuth refresh не входит в эту поставку).

Команды доступны всем зрителям; собственные сообщения бота игнорируются. `*`
означает всех текущих оппонентов owner, а не owner самого. Явный name также выбирает
только из этих оппонентов. Неизвестное/недопустимое имя возвращает `*` по требованию
пользователя. Имена с пробелами заключаются в двойные кавычки. При повреждённых
кавычках известная команда использует значения по умолчанию. Лишние аргументы
игнорируются; неизвестная команда игнорируется без события/КД.

| Команда | Аргументы после name | Значения по умолчанию |
| --- | --- | --- |
| swap | axis first second | axis случайно row/col; случайная допустимая пара |
| blur, shadow (алиас) | box | случайный блок |
| rotate, roll (алиас) | box | случайный блок |
| dance | box | случайный блок |
| gray | box | случайный блок |
| pulse | box | случайный блок |

Пользовательские номера начинаются с 1, протокол — с 0. Например:
`!swap * col 1 2`, `!blur "Игрок 2" 3`, `!rotate`.
Без name, но с args нужно явно писать `*`: `!blur * 3`.
Длительность/интенсивность не принимаются из чата, они в серверных настройках.
Пара first/second нормализуется совместно: если пара недопустима хотя бы для одной
цели, обе координаты получают одну случайную допустимую пару. Остальные валидные
параметры сохраняются. Дефолты выбираются один раз после определения целей.

Идентификатор сообщения Twitch обеспечивает дедупликацию даже при КД=0; его запись,
КД и эффекты фиксируются одной транзакцией. Для команд без message-id ничего не
применять (запрашиваются tags), повтор доставки не создаёт новый независимый эффект.
Дедупликация хранится 24 h с ключом bot-id/channel/message-id; при удалении/новой
привязке старое сообщение не должно примениться к новому лобби. Сверять время
сообщения с registeredAt и актуальный bindingId. Пишущих в чат ответов нет: статусы
подключения и ошибок отображаются на сайте.

Фоновый процесс использует отдельные worker_settings без `GameConfig.ready` /
`VoiceConfig.ready`, иначе запуск Django может очистить старые игровые комнаты.
Это же безопасное окружение применяется для офлайн fillSudoku.
